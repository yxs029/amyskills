## 一、迭代过程：以前怎么调研，现在怎么调研

### 1.1 v1.0 旧模式（2026-06-18 ~ 2026-08-20）

旧模式的核心是**「一个 cron 触发 → agent 全量调研 → 重写一份巨型 Markdown → 整个文件同步 Get笔记」**。

```
周四 cron 触发
  → agent 全网检索近 1 周西医/中医进展
  → 在原有 MD 上追加/重写"本次更新重点"
  → 药物组成、剂量、方案数据、医院信息、参考文献……全部堆进同一个 MD
  → 更新时间戳
  → 整个 MD（100KB+）同步到 Get笔记
```

**产出物**：两份独立的巨型 MD
- `直肠癌晚期治疗方案调研报告.md`（西医）—— 到 8-20 已 **147KB / 约 1700 行**
- `直肠癌晚期中医治疗方案调研报告.md`（中医）—— 到 8-20 已 **194KB / 1653 行**

旧自动化脚本 `cancer_weekly_update.py` 做的事很薄：只负责把这两份现成 MD 改个时间戳、整篇推给 Get笔记，**调研和写作本身全靠 agent 在 cron 里临场完成**。

### 1.2 v2.0 新模式（2026-08-24 上线，首跑 8/27-28）

新模式的核心是**「关注点分离」**：药物物料进数据库，报告只写方案索引；调研和产出去耦；可信度作为入库门禁。

```
周四 22:00  西医 cron（只调研写库，不产出）
  → 读 retro-checklist
  → 检索近 1 周西医进展
  → 可信度验证（A/B/C）后增量写入 drugs.db
  → 验证医院官网链接
  → 复盘 + 更新 checklist

周五 00:00  中医 cron（调研写库 + 统一产出）
  → 读 retro-checklist
  → 检索近 1 周中医进展 + 可信度验证 + 写库
  → 从 drugs.db 读【中西医全部数据】
  → export_to_site.py → data.json
  → generate_md.py   → 完整 MD（中西医都在）
  → generate_html.py → 交互式 HTML（tab 切换/搜索/筛选/弹窗）
  → website_deploy   → 公网 URL（手机可点）
  → 同步 Get笔记（生活家庭父母知识库）
  → 复盘 + 更新 checklist
```

**产出物**：
- `drugs.db`（SQLite，6 张表）—— 药物/方案/医院的长期资产，随周增长
- `直肠癌晚期_方案索引_{日期}.md` —— 桌面/Stand 阅读
- `cancer-report-site/index.html` —— 腾讯风格移动端交互页，部署公网
- Get笔记同步 —— 家人可查

### 1.3 新旧对比一览

| 维度 | v1.0 旧模式 | v2.0 新模式 |
|---|---|---|
| 数据载体 | 两份巨型 MD（147KB+194KB） | SQLite 药物库 + 轻量方案索引报告 |
| 药物详情 | 组成/剂量/机制全塞报告正文 | 只在 drugs.db，报告不写剂量 |
| 中西医关系 | 各写各的，两份独立文件 | 分开调研、统一产出，一份 HTML/MD 含全部 |

## 二、问题与解决：为什么要做这轮迭代

这轮迭代不是凭空想的，是旧模式跑了两个多月、问题堆到不得不改。下面原原本本复盘。

### 问题 1：单文件巨型 MD，手机根本没法看

**现象**：西医报告 147KB/1700 行，中医 194KB/1653 行。每周在顶部加「本次更新重点」，再把上周的挤成「上次更新重点」「上上次更新重点」……文件像滚雪球。

**为什么是问题**：这份报告是给家人看的，场景是手机。一个 200KB 的 MD 在手机上滑不到头，找不到自己关心的方案，药物剂量和方案描述混在一起，阅读体验很差。

**解决**：药物物料（组成/剂量/机制）外移到 SQLite，报告只写「方案能做什么 + 谁在做 + 去哪找」；同时做腾讯风格移动端 HTML，支持搜索、中西医 tab 切换、方案卡片弹窗。MD 保留给桌面/Stand 阅读。

### 问题 2：药物数据和报告内容耦合，无法复用

**现象**：药物组成、剂量、机制散落在 MD 正文的段落和表格里。同一个药在多个方案出现时要重复写，改一个剂量要全文找。

**为什么是问题**：药物本质是「物料清单」（BOM），是数据，不该硬编码在散文里。数据和叙述混在一起，既没法查询，也没法增量更新，更没法做「这个药被哪些方案引用」这种反向检索。

**解决**：设计 6 张表的规范化 schema（drugs / regimens / regimen_drugs / regimen_hospitals / reports / regimen_report_refs），外键级联。方案和药物多对多，一个药可被多方案引用。报告通过 `export_to_site.py` 从库里读数据生成，不再手写药物明细。

### 问题 3：无可信度把关，搜到了就加

**现象**：旧模式只要 agent 检索到一个医院/方案/药物就写进报告。医院官网链接有 16 个是错域名；有些方案来源单一甚至是宣传稿。

**为什么是问题**：这是医疗决策参考，不是资讯合集。一个打不开的医院官网、一个只有单一非权威来源的「新方案」，如果不加区分地和三甲医院/RCT 证据并列，家人可能误判。

**解决**：建立可信度三级门禁：
- **A（高）**：官网可访问 + ≥2 独立来源 + RCT/III 期证据
- **B（中）**：权威单源但缺多源验证
- **C（低）**：网站打不开/单一非权威源 —— 仍入库但标记 C，页面上视觉弱化

初始化时把已有 24 个方案评成 A9/B14/C1，24 家医院评成 A10/B11/C3，并程序化验证所有医院官网（修正 16 个错误域名）。**核心理念：不是搜到了就加，验证过了才加；C 级不删，但要让读者一眼看出这是低可信度。**

### 问题 4：西医中医同时产出，有 1 小时数据空窗

**现象**：原本设想两个 cron 都各自部署 HTML。如果西医先跑完部署了，而中医还没跑完，这 1 小时里公网页面只有西医数据、没有中医，家人看到的是「残缺版」。

**为什么是问题**：中西医是给同一场病的两套互补视角，缺一不可。而且两个任务同时跑还可能抢资源、产生不一致。

**解决**：改成**串行编排**——
- 周四 22:00 西医 cron：**只调研写库，不部署**
- 周五 00:00 中医 cron：先写中医的库，再从 drugs.db 读**中西医全部数据**统一产出一份完整 HTML/MD

中间留 2 小时缓冲，即使西医超时也不影响中医产出。彻底消除数据空窗。

### 问题 5：全量重写不可持续，且无自我改进机制

**现象**：每周全量重写/追加，报告越来越胖；跑完就跑完了，这周踩的坑下周可能再踩，没有沉淀。

**为什么是问题**：一个长期运行的自动化系统，如果没有反馈闭环，错误会重复发生，质量不会随时间提升。

**解决**：三件套——
1. **增量模式**：新增 `incremental` 周报模式，每周只产 200-400 行独立周报到 `周报/`，不碰主报告；需要时再 `compile` 汇编进主报告。
2. **复盘 Checklist**：中西医共用 `references/retro-checklist.md`，开跑前读、跑完复盘改进；只记待改进点（现象/为什么/方案/状态），不写流水账。
3. **自动停记**：连续 3 次无问题就只在开跑前扫一眼，不再写复盘；再出问题立即恢复并归零。

### 问题 6：工程细节坑（Windows 编码、SSL、链接校验）

- **中文编码**：PowerShell 5.1 默认 ANSI，Python 必须 `PYTHONIOENCODING=utf-8`，脚本里 `sys.stdout.reconfigure(encoding='utf-8')`。
- **SSL 证书**：企业代理环境下 requests 验证失败，用 `system-ca-certs.pem` + legacy SSL adapter 兜底。
- **医院域名错**：批量修正 16 个错误域名（如 `bucmsdsf.com` → `dsfy.cn`），对 403/521 的站点标记 `need-browser`。
- **MD 链接重复前缀**：`generate_md.py` 医院官网渲染成 `https://https://…`（已知小瑕疵，记入 checklist，不阻塞首跑）。

### 4.4 关键观察

1. **旧版最大问题是「单文件巨型 MD 全量重写」**——手机难读、数据与叙述混杂、无可信度把关、西医先部署有 1 小时空窗。
2. **本次迭代核心是「关注点分离」**——药物物料入 SQLite，报告只写方案索引；调研和产出去耦。
3. **可信度门禁是质变**——A/B/C 三级，C 级保留但弱化；修正 16 个错误医院域名；「不是搜到了就加」。
4. **双 cron 串行解决了数据空窗**——西医 22:00 只写库，中医 00:00 统一产出。
5. **工具链完全自研**——6 个 Python 脚本覆盖建库/导出/MD/HTML/链接校验/可信度初始化。
6. **端到端测试通过**——插入中西医各 1 条 C 级测试方案→导出→MD/HTML→部署→核对→清理→重新部署干净版。
7. **短板**：尚未经真实生产周验证（首跑 8/27-28）；商业/多用户/语义 RAG/长期路径未涉及；时间收益未量化。

## 六、我觉得还缺什么（Mavis 补充）

你让我看看还缺什么，我想了几点，供你参考：

1. **缺一次真实生产跑的验证**。目前全是端到端测试数据，8/27-28 首跑是第一次大考。双三角评分能到 69% 高阶，是「设计+工具链」分；真实周跑的稳定性要等首跑后才能确认。建议首跑后我做一次 30 天小复盘。
2. **缺回滚机制**。如果某次 cron 写库写进了脏数据（比如可信度评错、医院名拼错），目前只能手动 SQL 删。建议加一个「本周写入批次」标记（给 regimens 加 `batch_id` 或写一张 `runs` 表），出问题能一键回滚本周。
3. **缺 Get笔记同步的幂等**。如果中医 cron 跑到一半失败、重试，可能重复推笔记。建议按日期做 note_id 去重（同一期同一标题不重复推）。
4. **缺 cron 失败的主动通知**。你说主要用飞书，但这台机器没装 lark-cli。首跑万一失败，你不会立刻知道。建议要么我帮你把 lark-cli 装上配好通知，要么用 mavis cron 自身的汇报机制（跑完在本会话发消息）。
5. **缺家人侧的反馈闭环**。HTML 部署了，但家人用不用、看不看得懂、有没有点错，目前没有反馈。可以在 HTML 底部加一个极简反馈入口（哪怕是一个飞书表单链接）。

前两条（回滚 + 首跑验证）我建议优先，后三条可以等首跑稳了再说。你看哪些要加进 checklist 或下轮迭代。
