## 完整示例（Docker 容器 - V2.0 升级版）

```markdown
# 一页纸教程：Docker 容器

> **一句话定义**：基于 Linux namespace/cgroups 的轻量级应用隔离运行单元，共享宿主机内核。
> **大白话版**：把程序和它需要的所有东西装进「集装箱」，在任何机器上都能一样运行。

---

## WHAT — 是什么

**反差与本质**：
- **常识误区**：认为 Docker 只是一个"更轻量的虚拟机"。
- **底层本质**：Docker 本质上是**操作系统级别的进程隔离机制**，它不是在模拟硬件，而是在限制进程的视野和资源。

**层级拆解**：
| 层级 | 核心要素 | 具象化表现 |
| :--- | :--- | :--- |
| **宏观（编排层）** | Docker Swarm / K8s | 管理成百上千个集装箱的港口调度系统 |
| **中观（分发层）** | Registry / Image | 存储和传输集装箱的标准化图纸和仓库 |
| **微观（运行层）** | Container / Dockerfile | 正在运行的单个集装箱及其建造说明书 |

**谱系定位与共识**：
| Docker 容器 | 传统虚拟机 (VM) | 物理机 (裸金属) |
| :--- | :--- | :--- |
| 共享内核，秒级启动，MB级体积 | 独立内核，分钟级启动，GB级体积 | 独占硬件，部署周期长，资源利用率低 |

> **底层共识**：**环境一致性大于一切**。只要在本地能跑的镜像，在生产环境就一定能跑。

---

## WHY — 为什么重要

- **核心痛点**：解决了开发与运维之间永恒的矛盾——"在我的机器上明明是好的！"
- **价值主张**：相比虚拟机，容器镜像体积缩小 10-100 倍，启动时间从分钟级降至秒级，使微服务架构和持续集成/持续部署（CI/CD）成为可能。
- **跨界印证**：就像**集装箱彻底改变了全球物流业**（标准化尺寸让轮船、火车、卡车无缝衔接），Docker 彻底改变了软件交付业。

---

## HOW — 怎么做（核心步骤与高阶实战）

**价值对比（Before-After）**：
- **Before**：新员工入职，花 3 天时间对照着过期的 Wiki 文档安装各种环境依赖，最后还是报错。
- **After**：执行 `docker-compose up -d`，喝杯咖啡，3 分钟后整个微服务架构在本地完美运行。

**场景化步骤（以「部署一个带 Redis 的 Node.js 应用」为例）**：
1. **编写图纸**：创建 `Dockerfile`，定义 Node.js 基础环境和代码拷贝指令。
2. **定义编排**：创建 `docker-compose.yml`，声明 Node.js 服务和 Redis 服务的依赖关系。
3. **一键启动**：运行 `docker-compose up -d`，Docker 会自动拉取镜像、构建应用并连接网络。

**高阶实战案例（L5 级别应用：多阶段构建与安全加固）**：
- **背景**：某金融企业要求生产环境镜像体积极小，且绝对不能包含任何编译工具链以防黑客利用。
- **动作**：架构师采用 **Multi-stage Build（多阶段构建）**。在第一阶段（Builder）使用庞大的完整镜像编译 Go 代码；在第二阶段（Runner）使用极简的 `scratch`（空白镜像），仅将编译好的二进制文件拷贝过来。
- **结果**：镜像体积从 800MB 骤降至 15MB，且彻底消除了容器内的 Shell 和包管理器，安全性达到军工级。

**执行闭环**：
- **复盘机制**：每次构建镜像后，必须使用 `docker scout` 或 Trivy 扫描漏洞，确保没有引入高危 CVE。

## WHEN — 适用 vs. 不适用（精细化边界）

| 生效条件（必须满足） | 失效临界点（绝对不能用） |
| :--- | :--- |
| 应用是无状态的（Stateless）或状态已外部化 | 需要直接、独占地访问底层特定硬件设备（如某些加密狗） |
| 需要在多个环境（Dev/Test/Prod）中频繁流转 | 对操作系统内核版本有极度严苛的强绑定要求 |
| 架构设计允许随时被销毁和重建（Fail-fast） | 传统的、极其庞大的单体巨石应用（拆分成本高于容器化收益） |

---

## WATCH OUT — 常见误区

- **误区 1**：将数据库文件直接写在容器内部 → **正确做法**：必须使用 Volume（卷）挂载到宿主机，否则容器一删数据全没。
- **误区 2**：把 Docker 当虚拟机用，在一个容器里跑 N 个进程（Nginx+PHP+MySQL） → **正确做法**：遵循"一个容器只跑一个核心进程"的微服务哲学。
```
